## Product Lead 产品决策（§7 开放问题最终决定）

以下为 Plan §7「已知风险与开放问题」的产品决策，已纳入验收标准：

| # | 问题 | 产品决策 |
|---|------|---------|
| 1 | 3 个 preset 的 x:y 具体数值 | **Relaxed `30:5`、Default `25:5`、Strict `20:5`**（基于现有默认 600s 间隔 / 20s 休息时长的比率校准） |
| 2 | quota 满额的基准语义 | **100% = 一个完整工作周期（x 分钟）后耗尽至 0%；线性衰减** |
| 3 | 长休是否补少量小休 quota | **长休完成后补充 50% 的小休 quota**（避免长休后立即被小休骚扰） |
| 4 | 长休硬底线 N 的默认 | **120 分钟**（符合人机工程学建议的 2 小时上限） |
| 5 | "持续骚扰"的终止与退出 | **长休完成 → 退出持续骚扰；Idle/DnD/AppExclusion → 冻结累计时间，恢复后继续累计** |
| 6 | 🟢 档 OS toast 触发时机（新增，已确认） | **`on-threshold-cross`**：quota 跌破 70% 时发一次 toast 作为过渡预警；🟢 档内完全静默。防抖规则：必须补至 ≥80% 后才解锁下次跌破 70% 的 toast（避免 70% 附近抖动重复触发）。高级模式可配为 `silent` / `on-threshold-cross` / `periodic-N` 三选一 |
| 7 | 🟡/🟠 档软小窗触发间隔（新增，已确认） | **🟡 = 5 分钟，🟠 = 2 分钟**（三个 preset 共享同一套默认间隔；高级折叠可单独配置） |
| 8 | postponesLimit / postponableDurationPercent 在 quota 模式下的命运 | **quota 模式下完全不使用；preferences 条件隐藏这两项；electron-store 字段保留，切回经典时完全恢复** |
| 9 | 持续骚扰 base 值（新增，已确认） | **base = 10 分钟**（k=0 时每 10 分钟一次，k=9 时每 1 分钟一次；高级折叠可配） |
| 10 | 软提醒小窗是否自动消失（#UX-2，已确认） | **90 秒后自动消失，不扣 quota**（自用场景心流优先；不消失会在连续工作时积累视觉干扰；自动消失与"忽略"不同：不扣 quota，仅关闭窗口；下次提醒间隔到时正常再弹） |
| 11 | Advanced 阈值 slider 是否强制约束（#UX-3，已确认） | **强制约束：Yellow > Orange > Red**（反序阈值会造成档位永远不触发，是静默 bug 而非高级玩法；UI 层阻止用户设置反序值，slider 联动：调低 Yellow 时自动将 Orange 和 Red 同比调低以维持顺序） |

## 2. 按功能的验收标准

### 功能 1：调度模式开关

**描述**：preferences 界面新增"调度模式"选项，允许用户在「经典」和「Quota」之间切换。全新安装及升级用户默认为经典模式，Quota 为 opt-in。

**验收标准**：

| # | 验收条件 | 证据等级 | Layer | Tool |
|---|---------|---------|-------|------|
| 1.1 | `defaultSettings.js` 中存在 `schedulingMode` 字段，默认值为 `'classic'` | 文件审查 | L1 | 静态 |
| 1.2 | `electron-store` schema 包含 `schedulingMode` 字段，允许值为 `'classic'` 和 `'quota'` | 文件审查 | L1 | 静态 |
| 1.3 | preferences 界面存在调度模式切换 UI（单选或下拉），两个选项均可点击 | 手动验证 | L4 | — |
| 1.4 | 切换为 Quota 模式并重启应用后，`schedulingMode` 值在 electron-store 中持久化为 `'quota'` | 手动验证 | L4 | — |
| 1.5 | 切回经典模式并重启后，`schedulingMode` 值持久化为 `'classic'` | 手动验证 | L4 | — |

**边界情况**：
- [ ] `schedulingMode` 字段缺失（旧版 electron-store 数据）时，`electron-store` 使用默认值 `'classic'`，应用正常启动
- [ ] `schedulingMode` 值为非法字符串（如损坏配置）时，应用回退到 `'classic'` 并正常运行

**人工验证手册**（L4 条目 1.3–1.5）：

1. 启动应用，打开 preferences
2. 找到调度模式区域，确认默认选中「经典」
3. 选择「Quota」，关闭 preferences
4. 重启应用，打开 preferences，确认仍显示「Quota」被选中
5. 切回「经典」，重启应用，确认仍显示「经典」被选中

**预期表现**：模式切换即时响应，无需额外确认弹窗；重启后选择持久化。

**本功能不包含**：热切换（无需重启立即生效）不在本版本范围内（切换后下次启动生效即可）。

| 2.4 | 两条 quota 各自有独立的档位判定方法（返回 🟢/🟡/🟠/🔴 中的一个） | 单元测试 | L2 | 静态 |

**边界情况**：
- [ ] `miniBreakQuota` 尝试设置为 -1 时，被钳制为 0
- [ ] `longBreakQuota` 尝试设置为 101 时，被钳制为 100
- [ ] 两条 quota 同时处于不同档位（如 mini=🔴, long=🟢）时，各自独立触发对应提醒通道

**本功能不包含**：quota 档位 UI 渲染（在功能 6/7 中）。

### 功能 3：工作消耗 quota

**描述**：工作时间持续消耗 quota；消耗公式基于 x:y 比率（每 x 分钟工作使 quota 从 100% 降至 0%）；消耗频率 ≤ 1 Hz（事件驱动或低频轮询）。

**验收标准**：

| # | 验收条件 | 证据等级 | Layer | Tool |
|---|---------|---------|-------|------|
| 3.1 | Default preset（x=25）下，连续工作 25 分钟后 `miniBreakQuota` 消耗至 0（允许 ±2% 误差） | 单元测试 | L2 | 静态 |
| 3.2 | Relaxed preset（x=30）下，消耗速率为 Default 的 25/30≈83%（单元测试时间加速验证） | 单元测试 | L2 | 静态 |
| 3.3 | Strict preset（x=20）下，消耗速率为 Default 的 25/20=125%（单元测试时间加速验证） | 单元测试 | L2 | 静态 |
| 3.4 | `QuotaManager` 内部计时器间隔 ≥ 1000ms（不开高于 1 Hz 的定时器） | 文件审查 | L1 | 静态 |

**边界情况**：
- [ ] quota 已为 0 时继续工作，`miniBreakQuota` 保持在 0，不出现负值
- [ ] 工作消耗触发时 quota 模式未激活（经典模式），不执行任何消耗逻辑
- [ ] 应用在后台（最小化）期间，消耗逻辑仍正常执行

**本功能不包含**：longBreakQuota 的独立消耗公式（设计同 miniBreakQuota，使用相同 x:y 比率但独立计时）。

### 功能 4：休息补充 quota

**描述**：小休按时长线性补充 `miniBreakQuota`；长休按时长线性补充 `longBreakQuota`，同时额外补充 50% 的 `miniBreakQuota`。休息中途推迟/关闭则按已完成时长比例补充。

**验收标准**：

| # | 验收条件 | 证据等级 | Layer | Tool |
|---|---------|---------|-------|------|
| 4.1 | 小休完整完成（y=5 分钟）后，`miniBreakQuota` 恢复 100%（从 0 到 100） | 单元测试 | L2 | 静态 |
| 4.2 | 长休完整完成后，`longBreakQuota` 恢复 100%，`miniBreakQuota` 额外增加 50 点（钳制不超 100） | 单元测试 | L2 | 静态 |
| 4.3 | 小休完成 60% 时被推迟，`miniBreakQuota` 增加 60% 的单次补给量 | 单元测试 | L2 | 静态 |
| 4.4 | 长休完成 0% 时被忽略，`longBreakQuota` 和 `miniBreakQuota` 均不增加 | 单元测试 | L2 | 静态 |

**边界情况**：
- [ ] `miniBreakQuota` 已为 95，长休补充触发 +50，应被钳制为 100 而非 145
- [ ] 休息时长为 0 秒（立即推迟），补充量为 0

**本功能不包含**：经典模式下的补充逻辑（经典模式不触发 QuotaManager）。

### 功能 5：推迟扣 quota

**描述**：所有"忽略"行为额外扣 quota（在正常工作消耗之上叠加）：点「推迟」按钮、关软小窗、不点 toast、到建议时刻未休继续工作。🔴 档推迟扣 2× 普通推迟量。

**验收标准**：

| # | 验收条件 | 证据等级 | Layer | Tool |
|---|---------|---------|-------|------|
| 5.1 | 点击「推迟」按钮后，`miniBreakQuota` 在正常工作消耗基础上额外减少一个配置值（可查单元测试） | 单元测试 | L2 | 静态 |
| 5.2 | 关闭软提醒小窗（按「忽略」或关闭按钮）触发同等推迟扣减 | 单元测试 | L2 | 静态 |
| 5.3 | 🔴 档（quota < 10%）点击「推迟」时，扣减量为 🟡/🟠 档的 2 倍（单元测试） | 单元测试 | L2 | 静态 |
| 5.4 | OS toast 超时未点击（未交互）不额外扣减（仅工作时间持续消耗） | 单元测试 | L2 | 静态 |

**边界情况**：
- [ ] `miniBreakQuota` 已为 3，推迟扣减（假设 5 点），结果应为 0 而非 -2
- [ ] 经典模式下点「推迟」，不触发任何额外 quota 扣减
- [ ] 多次连续推迟时，每次独立扣减（不累加也不封顶）

**本功能不包含**：`PostponesLimit`（在 quota 模式下不使用，条件隐藏）。

### 功能 6：4 档提醒升级

**描述**：根据当前 quota 档位触发不同强度的提醒：🟢 >70%（仅托盘变色 + 可忽略 OS toast）→ 🟡 30-70%（角落软提醒小窗）→ 🟠 10-30%（软小窗 + OS toast 双发、间隔更短）→ 🔴 <10%（全屏 break 窗）。

**验收标准**：

| # | 验收条件 | 证据等级 | Layer | Tool |
|---|---------|---------|-------|------|
| 6.1 | `QuotaManager.getTier()` 返回 `'green'`（>70）、`'yellow'`（30-70）、`'orange'`（10-30）、`'red'`（<10） | 单元测试 | L2 | 静态 |
| 6.2 | quota 从 75% 跌至 69%（跨越 🟢→🟡 边界）时，`BreaksPlanner` 收到档位变更事件并调整下次提醒类型 | 单元测试 | L2 | 静态 |
| 6.3 | quota 从 15% 跌至 9%（跨越 🟠→🔴 边界）时，`BreaksPlanner` 切换为全屏 break 窗 | 单元测试 | L2 | 静态 |
| 6.4 | `defaultSettings.js` 中 🟠 档提醒间隔默认值 < 🟡 档默认值（具体：🟡=5min，🟠=2min） | 文件审查 | L1 | 静态 |
| 6.5 | `defaultSettings.js` 中 🟢 档 toast 行为字段存在，默认值为 `'on-threshold-cross'`，允许值包含 `'silent'`、`'on-threshold-cross'`、`'periodic-N'` | 文件审查 | L1 | 静态 |
| 6.6 | 🟢 档防抖：quota 跌破 70% 触发 toast 后，必须回升至 ≥80% 才解锁下次跌破 70% 的 toast（单元测试：跌至 69% → 升至 75% → 再跌至 69%，第二次不触发 toast） | 单元测试 | L2 | 静态 |
| 6.7 | 🟢 档防抖：quota 跌破 70% 触发 toast 后，回升至 80% 以上再次跌破 70%，第二次正确触发 toast（解锁验证） | 单元测试 | L2 | 静态 |

**边界情况**：
- [ ] quota 恰好为 70% 时，归属 🟡 档（边界包含在低档位侧：>70 为 🟢，≤70 且 ≥30 为 🟡）
- [ ] quota 恰好为 30% 时，归属 🟡 档
- [ ] quota 恰好为 10% 时，归属 🔴 档（<10 为 🔴，≤30 且 >10 为 🟠）
- [ ] quota 从 🔴 档通过休息回升至 🟡 档后，全屏窗口正确消失，改为软提醒小窗
- [ ] 🟢 档行为配置为 `'silent'` 时，quota 跌破 70% 不发任何 toast

**本功能不包含**：档位提醒 UI 的具体交互细节（在功能 7 中）。

| # | 验收条件 | 证据等级 | Layer | Tool |

| 7.2 | 软提醒小窗显示 miniBreakQuota 和 longBreakQuota 两条进度条 | 手动验证 | L4 | — |
| 7.3 | 点击「现在休」立即触发对应档位的休息（🟡 触发小休，🟠 触发小休+双发 toast） | 手动验证 | L4 | — |
| 7.4 | 点击「+2 分」推迟 2 分钟，窗口关闭，触发推迟扣 quota | 手动验证 | L4 | — |

| 7.8 | 小窗出现在屏幕角落（默认右下角）而非屏幕中央 | 手动验证 | L4 | — |
| 7.9 | 小窗出现 90 秒后无用户操作时自动消失，不扣 quota（与"忽略"行为不同） | 单元测试 | L2 | 静态 |
| 7.10 | 小窗自动消失后，下次提醒间隔（🟡=5min / 🟠=2min）到时正常再次弹出 | 单元测试 | L2 | 静态 |

**边界情况**：
- [ ] 多显示器环境下，小窗出现在主显示器的右下角
- [ ] quota 档位在小窗显示期间变化（如从 🟡 跌至 🔴），小窗关闭，切换为全屏 break 窗
- [ ] 快速连续点击「+2 分」两次，只触发一次推迟（防抖处理）
- [ ] 小窗在第 89 秒时用户点击「忽略」，应触发推迟扣 quota（而非无代价消失）
- [ ] 小窗在自动消失倒计时期间 quota 跌至 🔴，立即关闭并切换全屏 break 窗（不等 90 秒）

**人工验证手册**（L4 条目 7.2–7.8）：

1. 将 quota 手动调低至 🟡 档（可通过 preferences 调整参数或等待消耗）
2. 观察屏幕角落是否出现软提醒小窗
3. 在其他窗口（如终端或文本编辑器）中持续输入文字，确认焦点未被抢走
4. 使用 Tab 键在三个按钮间切换，确认焦点环可见
5. 按 Enter 激活「现在休」，确认进入休息流程
6. 重新触发提醒，按 Esc，确认窗口关闭
7. 重新触发提醒，点击「+2 分」，确认 2 分钟后再次出现
8. 重新触发提醒，点击「忽略」，确认窗口关闭并 quota 有扣减

- [ ] **性能**：quota 消耗计时器间隔 ≥ 1000ms（≤ 1 Hz），不开高频定时器；被动时间（冻结）期间零 CPU 活动（Layer L1，文件审查验证计时器配置）
- [ ] **跨平台**：Windows / macOS / Linux 三平台可正常启动并运行 quota 模式（Layer L4，用户在自己机器上手动验证 macOS；Windows/Linux 为可选验证）

## 4. 已知限制

| 限制 | 原因 | 影响 |
|------|------|------|
| Wayland 软提醒小窗定位可能不准确 | Electron BrowserWindow 在 Wayland 历史上有定位限制 | 可回退到屏幕中央或 OS toast；不影响功能本身 |
| OS toast 点击行为无法自动化测试 | Electron toast 通过 processWin 的 renderer 发出，测试环境无法模拟 | 🟢 档 toast 验收为 L4（人工） |
| 真实 idle 检测依赖 node-desktop-idle-v2 | 无法在 CI 环境模拟真实 idle | quota 冻结测试通过 mock pause/resume 事件替代 |
| Electron 托盘图标自动化困难 | playwright-cli 对 Electron 原生 tray 无法控制 | 托盘相关验收均标为 L4（人工） |
| soft-reminder 进度条颜色使用硬编码阈值 70/30/10 | getTierClass() 未读取 settings 中的自定义阈值 | 用户在高级模式修改默认阈值时，进度条 CSS 色可能与状态机实际档位不一致；quota 逻辑本身不受影响（v1.22 backlog） |
| `__quotaState__` 持久化写入 `isFrozen` 字段但启动时从不读回 | _persistToSettings() 包含 isFrozen 但 start() 始终以空 Set 初始化 | 行为正确（重启后正确不冻结），仅多存一个无用字段，增加微量 store 体积（v1.22 可清理） |

## 8. 健康评分配置

*由 Product Lead 在版本启动前填写；产品 QA 在验收时按此配置评分。*

### 8.1 本版本权重配置

本版本为 Electron 桌面应用，有 UI 交互但 QA 验收以单元测试和人工验证为主。调整视觉质量权重下降，功能正确性和边界情况权重上升（逻辑正确比视觉精细更重要）。

| 维度 | 本版本权重 | 调整原因 |
|------|-----------|---------|
| 功能正确性 | 30% | quota 状态机逻辑正确是核心，权重提升 |
| 用户体验 | 15% | 软提醒小窗和提醒档位的使用体验 |
| 视觉质量 | 10% | 自用 fork，视觉精细度次要 |
| 错误处理 | 12% | 异常 quota 值、store 损坏等边界处理 |
| 边界情况 | 13% | quota 边界（0/100/冻结/重置/硬底线）权重提升 |
| 性能感知 | 8% | 计时器频率和后台 CPU 占用 |
| 内容质量 | 7% | i18n 文案准确性 |
| 可访问性 | 5% | 键盘操作支持 |
| **合计** | **100%** | |

### 8.2 评分标准

| 评级 | 分数区间 | 含义 | 处理方式 |
