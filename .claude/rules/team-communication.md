# 团队通信规范

本规范适用于团队中的所有 Agent。

## 职责边界

每项决策都有明确的归属方。**不存在"由双方协商"的模糊地带。**

### 技术决策（归架构师）

架构师对以下决策拥有最终决定权，无需 Product Lead 或 Coordinator 审批：

- 接口设计（API 契约、数据结构、模块边界）
- 技术选型（框架、库、工具链）
- 架构方案（模块拆分、分层设计、依赖方向）
- 依赖选择（引入或移除第三方依赖）
- 实现细节（算法、代码结构、性能优化）

### 产品/UX 决策（归 Product Lead）

Product Lead 对以下决策拥有最终决定权，无需架构师审批：

- 用户流程（任务路径、引导逻辑、入口设计）
- 信息架构（内容组织、导航结构、层级关系）
- 验收标准（功能是否符合用户需求的判断依据）
- UX 方向审批（确认 UX 规格与产品目标对齐，不干预交互实现细节）

### 交互设计决策（归 UX Designer）⚠️ 仅 UX 密集型项目

UX Designer 对以下决策拥有最终决定权，无需 Product Lead 逐一审批：

- 用户交互（交互逻辑、操作流程、反馈机制）
- 交互细节（动效时机、状态转换、错误提示方式）
- 界面信息层级（组件粒度的内容排布）

**三权分立（UX 密集型模式）**：
- **Product Lead**：做什么功能、优先级、验收标准 → 审批 UX 方向是否对齐
- **UX Designer**：用户怎么操作、交互怎么流转、反馈怎么给 → 交互设计决策权
- **架构师**：技术怎么实现、接口怎么定 → 技术决策权

### 冲突裁定

当技术可行性与产品需求发生冲突时：

1. 架构师与 Product Lead 直接沟通，说明各自约束
2. 双方无法达成一致时，**Coordinator 有最终裁定权**
3. 裁定结果通知双方 Leader，追溯员记录决策

## 直接通信

- **团队内部**：直接与队友沟通，无需转发。
- **跨团队**：可以直接与任何 Agent 沟通。但跨团队沟通产生的 **决策** 必须通知：
  - 双方的团队 Leader（架构师负责技术团队，Product Lead 负责产品团队）
  - Coordinator/CEO

## Per-task Agent 通信范围

**开发（developer）、CR（code-reviewer）、技术 QA（tech-qa）** 均为 per-task Agent：每个任务独立启动，任务完成后关闭。

Per-task Agent 的通信范围限于当前任务相关的角色：

| Per-task Agent | 可通信的角色 | 禁止通信 |
|---------------|-------------|---------|
| developer（T\<NNN>） | 架构师、CR（同任务）、tech-QA（同任务） | 其他任务的 developer/CR/tech-QA |
| code-reviewer（T\<NNN>） | 开发（同任务）、架构师 | 其他任务的任何 per-task Agent |
| tech-qa（T\<NNN>） | 架构师、开发（同任务） | 其他任务的任何 per-task Agent |

**原则**：per-task Agent 的生命周期与其任务绑定，不积累跨任务上下文，不干预其他任务的工作。跨任务协调由架构师统一处理。

## 消息格式

保持消息简洁。使用以下结构：

```
状态：[发生了什么]
结论：[你的评估/决定]
需要：[你需要对方做什么，如果有的话]
```

不要发送长篇叙述。接收方的 context 窗口有限。

## 任务创建

**只有 Coordinator 创建任务。** 如果你需要新任务：

1. 向你的 Leader 汇报需求和详情
2. Leader 评估后通知 Coordinator
3. Coordinator 创建任务并分配

> 任务交付阶段定义（五阶段）→ 详见 docs/knowledge/code-delivery-stages.md
> 汇报频率、通知要求、消息确认、超时处理、证据标准 → 详见各 agent prompt（v5.3.0 嵌入）

## 冲突解决

1. **团队内部**：Leader 解决
2. **跨团队（技术类）**：架构师有最终决定权
3. **跨团队（产品类）**：Product Lead 评估，Coordinator 审批
4. **无法解决**：Coordinator 咨询用户
